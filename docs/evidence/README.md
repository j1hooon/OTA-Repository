# 증거 색인

각 실험의 **방법, 결과, 증명한 것, 증명하지 못한 것**을 정리했습니다. 원본 로그는 같은 폴더의 하위 디렉터리에 있습니다.
공개 저장소라서 로그의 집 공인 IP는 `<ONPREM_PUBLIC_IP>`로 치환되어 있습니다. 로그 안의 시각은 KST이고, `git=` 항목은 실험 당시의 커밋입니다(이력 정리로 일부 SHA는 현재 이력에 존재하지 않습니다).

| 실험 | 폴더 | 측정 횟수 | 스크립트 |
|---|---|---|---|
| HAProxy 절체 (3가지 체크 간격) | `failover-inter{1000,500,250}/` | 각 10 | `scripts/measure-failover.sh` |
| DNS 전환·복귀 (에이전트 중단) | `dns-failover/run{1,2,3}.log`, `summary.csv` | 3 | `scripts/measure-dns-failover.sh` |
| DNS 플래핑 (2시간) | `dns-failover/flap.log` | 1 (표본 478) | `scripts/measure-dns-flap.sh` |
| DR 종단: 에이전트 중단 | `dr-e2e/` | 1 | `scripts/measure-dr-e2e.sh` |
| DR 종단: HAProxy 중지 | `dr-e2e-l7/` | 1 | 동일 (`FAULT=l7`) |
| DR 종단: 앱 전부 중단 | `dr-e2e-apps/` | 1 | 동일 (`FAULT=apps`) |
| DR 큐 반영 | `dr-e2e/drain.log`, `db-after-drain.log` | 1 | `scripts/drain-dr-queue.py` |
| 기기 상태 수집 유실 | `status-ingest/loss-test.md` | 1 | 수동 절차 |

## 1. HAProxy 절체

- **방법**: Active 노드의 NodePort(30080)를 iptables raw 테이블에서 차단해 장애를 만들고, mgmt에서 0.1초 간격으로 HAProxy(`:8000/health`)에 병렬 요청을 보냅니다. 장애 주입부터 Standby가 처음 200을 응답한 요청의 시작 시각까지를 RTO로, 장애 해제부터 Active가 다시 응답한 시각까지를 복귀 시간으로 기록합니다.
- **결과** (각 n=10, 단위 ms)

| `inter` | RTO 중앙값 | RTO 범위 | 복귀 중앙값 | 실패 요청 중앙값 |
|---|---|---|---|---|
| 1000ms | 3652 | 3135~4060 | 2414 | 35.5 |
| 500ms (채택) | 1772 | 1614~1929 | 1074 | 16.5 |
| 250ms | 958 | 807~1018 | 572 | 8.5 |

- **증명한 것**: 체크 간격에 비례해 절체 시간이 줄어듭니다. 채택값에서 절체는 약 1.8초이고, 절체 구간에 실패한 요청은 약 16건(0.1초 간격 폴링 기준)입니다.
- **한계**: 관측 지점이 mgmt입니다(실제 기기까지의 경로 아님). 주입·해제 시각은 `ssh` 반환 시점이라 수십 ms의 오차가 있습니다. `250ms`의 오탐 위험은 측정하지 않았습니다.

## 2. DNS 전환·복귀

- **방법**: mgmt의 하트비트 에이전트를 중단하고 3초 간격으로 권한 서버와 공개 리졸버(8.8.8.8)의 응답을 조회해, 응답이 DR IP로 **3회 연속** 일치하면 전환으로 확정합니다. 에이전트를 재개한 뒤 PRIMARY 복귀를 같은 방식으로 측정합니다. PC 절전으로 시계가 건너뛴 회차를 무효 처리하는 장치가 있습니다.
- **결과** (n=3, 단위 초)

| 항목 | 중앙값 | 범위 |
|---|---|---|
| 전환 (권한 서버) | 333 | 314~381 |
| 전환 (공개 리졸버) | 346 | 328~381 |
| 복귀 (권한 서버) | 40 | 33~80 |

- **증명한 것**: 하트비트가 끊기면 약 5~6분 안에 DNS가 DR로 바뀌고, 재개되면 1~2분 안에 돌아옵니다.
- **한계**: 복귀의 공개 리졸버 값은 캐시 때문에 불안정(4~126초)해서 신뢰하지 않습니다. 전환 시간의 구성 요인은 분해하지 않았습니다. 알람은 전환 중 `OK`로 남았고(원인은 추정), `alarm_s` 열이 `none`인 이유입니다.

## 3. DNS 플래핑 검사

- **방법**: 2시간 동안 15초 간격으로 권한 서버를 조회하면서 같은 시간에 Jenkins 빌드를 돌려 부하를 줍니다. PRIMARY가 아닌 응답이나 무응답, 하트비트 비정상을 이탈로 셉니다.
- **결과**: 표본 478, 이탈 0, 무응답 0, 하트비트 비정상 0 → PASS
- **증명한 것**: 빌드 부하가 있는 정상 운영 중에는 오탐으로 DR로 넘어가지 않았습니다.
- **한계**: 1회, 2시간짜리 관찰입니다.

## 4. DR 종단 시나리오

- **방법**: 장애를 주입하고 DNS가 DR IP로 확정되면, 요청마다 공개 리졸버에 새로 물어 DR IP가 안내될 때만 그 IP로 `/ota/check` 10번을 보냅니다. 옛 값(온프레미스 IP)이 안내되면 `stale`로 세고 보내지 않습니다. 이후 `/ota/report`를 보내 큐 보관 응답을 확인하고, 장애를 해제해 복귀 시간을 잽니다. 테스트 이벤트는 실제 기기 행을 건드리지 않도록 전용 기기 ID(`e2e-probe`)를 씁니다.
- **결과** (각 n=1, 단위 초)

| 장애 | 권한 서버 전환 | 리졸버 전환 | DR 첫 정상 응답 | DR 처리 | stale | 보고 | 복귀 |
|---|---|---|---|---|---|---|---|
| 에이전트 중단 | 343 | 379 | 386 | 10/10 | (측정 전 방식) | `QUEUED_IN_REDIS_AOF` | 57 |
| HAProxy 중지 | 342 | 374 | 380 | 9/10 | 1 | `QUEUED_IN_REDIS_AOF` | 54 |
| 앱 전부 중단 | 324 | 354 | 364 | 7/10 | 3 | `QUEUED_IN_REDIS_AOF` | 54 |

- **증명한 것**: 서로 다른 세 가지 장애에서 모두 하트비트가 끊기고 DNS가 DR로 바뀌며, 그 이름으로 보낸 요청을 DR이 처리합니다. DB 복제본이 읽기 전용이라 보고는 Redis 큐에 보관됩니다.
- **한계**: 각 1회입니다. `에이전트 중단` 행은 요청을 전환 직후 한 번 조회한 IP로 보내던 초기 방식으로 측정해 `stale`을 따로 세지 않았습니다. 같은 방식으로 `HAProxy 중지`를 처음 측정했을 때는 리졸버가 옛 값을 안내해 0/10이 나왔고(DR 자체는 정상), 이것이 요청마다 재조회하는 현재 방식으로 바꾼 이유입니다. 온프레미스가 외부에서 도달할 수 없는 랩이라 장애 **전** PRIMARY로 실제 요청이 가는지는 확인하지 않았습니다.

## 5. DR 큐 반영

- **방법**: DR에서 쌓인 보고를 `scripts/drain-dr-queue.py`로 원본 PostgreSQL에 반영하고, 반영 직후 `ota_deployment_history`를 조회했습니다.
- **결과**: 읽음 2 = 신규 반영 2 + 중복 0 + dead-letter 0, 큐 남은 0. 조회 결과에서 `handled_by_cluster = dr`이고 `completed_at`이 DR이 접수한 시각(반영 시각이 아님)입니다.
- **증명한 것**: DR 동안 보관된 보고가 원본 DB에 접수 시각을 유지한 채 반영됩니다.
- **한계**: 운영 데이터는 2건입니다. 멱등성, dead-letter, 부분 실패 후 재실행은 합성 데이터로 실제 PostgreSQL 16과 Redis 7에서 시험했지만 그 결과 로그는 보관하지 않았습니다. 반영은 수동이며, 반영 시 기기 현재 버전을 더 새로운 이벤트일 때만 갱신합니다.

## 6. 기기 상태 수집 유실

- **방법**: 두 클러스터의 소비자를 중단하고 가상 기기로 상태 메시지 3건을 발행한 뒤 소비자를 복구해 건수를 비교했습니다.
- **결과**: 1건 → (중단 중) 1건 → (복구 후) 4건. 유실과 중복이 없습니다.
- **한계**: 소비자 중단 시나리오 1회입니다. DB 장애나 K3s 절체 중의 유실은 검증하지 않았습니다.
